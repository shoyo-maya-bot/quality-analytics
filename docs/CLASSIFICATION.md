# 指摘の分類

分類の正は `config/taxonomy.yaml` です。このページは考え方と使い方の説明です。

## なぜ 3 つの軸で分けるか

| 軸 | 答える問い | 使い道 |
|---|---|---|
| type（種類） | その指摘は品質に効くか | 欠陥（A）の数で成果物の品質を、ノイズ（B）の割合でレビューの効率を見る |
| topic（観点） | どこで欠陥が出ているか | レビューの観点（office-review の checks.yaml）や設計書のテンプレートを強化する場所を決める |
| root_cause（真因） | なぜ作成者が書けなかったか | 作成時の手当て（教育・チェックリスト・事前の確認会）を決める |

指摘の件数だけを数えると、表記の指摘が多いレビュアーほど「よく見ている」ように見えてしまいます。
種類で分けると、欠陥を見つけたレビューと、体裁を整えたレビューを区別できます。

## type の判断

| 迷う例 | 分類 | 理由 |
|---|---|---|
| NITS だが、桁の数字が間違っている | A2 | 重要度ではなく内容で決める |
| MUST だが「この書き方の方が好み」 | B2 | 直さなくても品質は変わらない |
| 「〜は考慮されていますか？」 | C1 | 回答で考慮漏れと分かれば、別の A の指摘として起票し直す |
| 既に書いてあることへの指摘 | B3 | 指摘者の読み落とし。多い場合は設計書の構成（見つけにくさ）も疑う |
| 「適宜」「など」「必要に応じて」 | A3 | 実装者によって振る舞いが変わる |

## root_cause の判断

指摘の本文から真因まで分かることは多くありません。本文で判断できないときは空のままにします（推測で埋めない）。
振り返りの場で作成者と話して付け直すと、最も精度が上がります（`data/findings.csv` を Excel で直して `qa check`）。

| 真因 | 典型的な指摘 | 手当ての例 |
|---|---|---|
| R1 業務・要件の理解不足 | 業務の流れと違う、要件を取り違えている | 業務の説明会、用語集 |
| R2 前提・制約の確認漏れ | 上限・境界・同時実行・タイムゾーン・0 件 | 例外ケースのチェックリスト |
| R3 他成果物との整合確認漏れ | 上位の設計書や一覧と食い違う | 突き合わせの手順、design-diff の整合チェック |
| R4 標準・規約の理解不足 | 命名規則・記述ルール違反 | 規約の要点の共有、機械チェック |
| R5 セルフチェック不足 | 転記ミス、修正漏れ | 提出前のセルフチェックリスト |
| R6 記述の技術 | 内容は正しいが伝わらない | 記述のテンプレート・良い例の共有 |

## 分類を変えるとき

1. `config/taxonomy.yaml` を直し、`version` を上げる（LLM 分類のキャッシュが分類し直しになる）
2. `prompts/`（工程の目安）と `config/rules.yaml`（キーワード）を合わせる
3. `qa classify --mode rules --overwrite` などで分類し直し、`qa check` で確かめる

過去の分析と比べるときは、同じ version の分類どうしで比べてください。
